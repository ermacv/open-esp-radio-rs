# Register workspace and SVD export

The register workspace keeps machine observations and human conclusions in
different files:

- `facts` is regenerated by `mmio discover`; do not edit it;
- `overlay` contains reviewed names, fields, access semantics, reset metadata,
  ignored false positives, and explicitly manual additions.

Configure both paths in `vendor-validator.toml`:

```toml
[registers]
facts = "generated/findings/mmio.json"
overlay = "registers/reviewed.toml"
```

Relative paths are resolved from the project manifest. When `[registers]` is
configured, `mmio discover --project ...` uses `facts` as its default
`--json-report`; an explicit `--json-report` still wins.

## Bootstrap and daily workflow

Generate fresh observations from the project memory-map ranges and local
artifacts:

```console
cargo vendor-code-validator mmio discover \
  --project validation/esp32s31/vendor-validator.toml \
  --run-spec /path/to/local.run
```

Create a minimal overlay once:

```console
cargo vendor-code-validator registers init-overlay \
  --project validation/esp32s31/vendor-validator.toml
```

The command refuses to overwrite an existing overlay. Use `--output PATH` to
create a separate draft. It creates one peripheral entry for every discovery
range and leaves register decisions for review.

After editing, validate identities and provenance:

```console
cargo vendor-code-validator registers validate \
  --project validation/esp32s31/vendor-validator.toml
```

Finally export a merged SVD:

```console
cargo vendor-code-validator registers export-svd \
  --project validation/esp32s31/vendor-validator.toml \
  --output generated/svd/vendor-radio.svd
```

The default export includes every non-ignored observation. Registers without
an overlay receive stable names such as `REG_00000020_W32` and descriptions
that mark them unreviewed. `--reviewed-only` emits only reviewed and manually
added registers, which is useful for a conservative PAC input.

## Overlay format

```toml
schema = 1
device-name = "ESP32S31_RADIO_REVIEW"
vendor = "Espressif"
version = "0.1"
description = "Reverse-engineered radio register map"
address-unit-bits = 8
width = 32

[[peripherals]]
range = "modem-radio-core"
name = "MODEM_RADIO"
description = "Reviewed modem and radio registers"

[[registers]]
address = 0x2010d830
width = 32
status = "reviewed"
name = "WAKE_CONTROL"
description = "Modem wake control"
access = "read-write"

[[registers.fields]]
name = "WAKE_ENABLE"
lsb = 21
width = 1
origin = "write-pattern"

[[registers.fields]]
name = "UNKNOWN_MODE"
lsb = 24
width = 2
origin = "manual"
```

Names follow CMSIS-SVD/ANSI C identifier rules. Peripheral `range` refers to a
named half-open discovery range, so its base address remains attached to the
generated evidence rather than being copied into the overlay.

Register status has explicit meaning:

| Status | Required evidence and export behavior |
| --- | --- |
| `reviewed` | The exact `(address, width)` must exist in current facts; the register is exported with the reviewed name |
| `ignored` | The exact observation must exist but is excluded from SVD; fields are forbidden |
| `manual` | The address must be inside a discovery range and absent from facts; it is exported as an explicit human addition |

An omitted status means `reviewed`. A stale reviewed/ignored entry fails
validation instead of silently becoming manual after a new vendor revision.

Field `origin` defaults to `manual`. `origin = "write-pattern"` is stronger:
at least one observed modified-bit mask must cover the entire field range.
This links a proposed field boundary to concrete code evidence without
claiming a field name or hardware behavior.

The overlay accepts optional CMSIS-SVD semantics:

- register and field `access`;
- paired `reset-value` and `reset-mask`;
- field `modified-write-values`, including `oneToClear`;
- field `read-action`.

Values are checked against the CMSIS-SVD vocabulary and register width. Fields
must be non-empty, non-overlapping, and contained in the register.

## Evidence boundary

Discovery may infer observed access width, users, ordered accesses and modified
bit candidates. It cannot infer authoritative register/field names, reset
state, W1C behavior, read side effects, reserved bits, or whether an
unobserved access is illegal. Those properties enter only through the overlay.

The SVD is therefore a materialized view, not the source of truth:

```text
vendor ELF/archive + memory ranges
              |
              v
      generated MMIO facts  +  reviewed overlay
                         \      /
                          v    v
                       CMSIS-SVD
```

Regeneration replaces facts while preserving review. `registers validate`
then reports stale identities before another SVD is produced. The project
doctor exposes the same readiness and coverage counts.

The generated SVD uses schema version `1.3` and is intended to validate against
the [official CMSIS-SVD 1.3 schema](https://arm-software.github.io/CMSIS_5/SVD/html/schema_1_2_gr.html).
It may be supplied to later validator runs or PAC generation after it exists.
Avoid making a not-yet-generated SVD a mandatory discovery input, which would
introduce a bootstrap cycle.

Generated facts include local artifact paths and hashes for reproducibility.
Review them before committing to a public repository. The overlay contains no
artifact paths and is the normal shareable project asset.
