# Reviewed function and context packs

The function workspace turns generated linked IR into a stable manual-review
project without pretending that recovered pseudo-code is vendor source. It
joins two required inputs and one optional reviewed view:

- schema-v40 linked-IR reports generated by configured `[[analysis.ir]]`
  profiles;
- one human-edited pack containing reviewed function names, roles, summaries,
  and names for observed context arguments and fields.
- validated interface bindings, when an initialized `[interfaces].pack` is
  present in the same project.

The linked IR remains the source of call paths, MMIO, delays, external semantic
operations, event dispatches, trampoline calls, context offsets, and
pseudo-code. The pack supplies presentation and review decisions only.

## Ownership boundary

Keep each claim in one project layer:

| Claim | Owner |
| --- | --- |
| Function bytes, identity, call closure, pseudo-code and context accesses | generated linked IR |
| Human function name, architectural role and one-line summary | function pack |
| Human context/type/field names and display types | function pack |
| Register/bit name, access policy, reset value and W1C semantics | register model |
| Callback-table layout, ABI and slot identity | interface pack |
| Reusable RTOS, NVS, logging and delay meaning | semantic catalog |
| Rust replacement and behavioral equivalence | implementation plus verification contracts |

This prevents a convenient pseudo-function name from silently becoming a
hardware, ABI, scheduler, or equivalence claim. The generic analyzer has no
RTOS or ESP32-specific names. The function renderer may join validated
interface bindings at exact static call sites without changing the linked IR
or backend behavior. Slot meaning still comes only from the reviewed
interface pack and semantic catalog.

## Project configuration

Select one or more linked-IR profiles and configure the reviewed and generated
paths relative to `vendor-project.toml`:

```toml
[functions]
pack = "functions/reviewed.toml"
profiles = ["rom-phy", "archive-phy"]

[functions.review]
output = "generated/reports/function-review.md"
```

If `profiles` is omitted, every `[[analysis.ir]]` profile is selected. Profile
IDs must exist and may not repeat. The workspace currently accepts only
schema-v40 `ir export` reports with `completeness_claim = false`; schema drift
fails closed instead of being interpreted approximately.

## Bootstrap and daily workflow

Generate the configured IR first:

```console
cargo vendor-binary-workbench ir build \
  --project path/to/vendor-project.toml \
  --run-spec /path/to/local.toml
```

Create the reviewed pack once:

```console
cargo vendor-binary-workbench functions init-pack \
  --project path/to/vendor-project.toml
```

`init-pack` writes the selected artifact provenance guards and an otherwise
empty schema-v3 sparse overlay. It refuses to overwrite an existing pack.
Add only reviewed or ignored decisions; omitted generated functions, contexts,
fields and logical-type fields remain visible as computed unreviewed backlog.
`--output PATH` can create a disposable draft.

Edit the pack and validate it:

```console
cargo vendor-binary-workbench functions validate \
  --project path/to/vendor-project.toml

cargo vendor-binary-workbench functions validate \
  --project path/to/vendor-project.toml \
  --deny-unreviewed
```

Normal validation rejects stale artifact digests, stale function identities,
stale context fields, duplicate reviewed names, invalid identifiers, and
implicit acceptance of incomplete evidence. It allows an incremental review.
`--deny-unreviewed` additionally makes any unreviewed root function, context,
or observed field an unsuccessful result.

Lifecycle commands use one typed result model each. The default view uses
coverage tables for functions, contexts and fields; JSON/JSONL emits the
corresponding typed report directly. When strict coverage fails, validation reports `status =
"unreviewed"` together with `deny_unreviewed = true`; it never labels a failed
policy gate as valid.

Render the reading view after each edit:

```console
cargo vendor-binary-workbench functions review \
  --project path/to/vendor-project.toml

cargo vendor-binary-workbench functions review \
  --project path/to/vendor-project.toml \
  --check
```

The Markdown report combines detailed pseudo-code and joined evidence only for
explicitly reviewed functions. Omitted and ignored functions appear in compact
inventories with closure, call, MMIO, context, semantic and blocker counts.
Complete generated pseudo-code remains in each profile's `.pseudo.rs` output,
linked IR and the TUI. This keeps an artifact-wide project readable without
discarding evidence. The report is generated navigation material and must not
be edited.
`--output PATH` overrides the project destination; `--check` compares without
writing.

`project analyze` regenerates linked IR and this report, then validates the
pack. `project analyze --check` reproduces and compares both outputs without
mutation. Neither mode initializes or edits the reviewed pack.

## Pack format

The pack begins with exact provenance guards:

```toml
schema = 3
id = "esp32s31-radio-rev0"

[[inputs]]
profile = "rom-phy"
source = "rom"
artifact-sha256 = "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
```

The key is `(profile, source)`. Every generated input requires exactly one
lowercase SHA-256 guard. Updating a vendor artifact therefore requires an
explicit re-review; copying old names to new bytes is never automatic.

A reviewed function makes three separate human claims:

```toml
[[functions]]
profile = "rom-phy"
source = "rom"
identity = "rom::phy_enable"
status = "reviewed"
name = "enable_radio_phy"
role = "phy.lifecycle.enable"
summary = "Initializes the radio PHY and enables its calibrated runtime state."
```

`name` must be a Rust-like identifier. `role` is a stable dotted ID chosen by
the project. `summary` is one line. These fields are required for `reviewed`
and forbidden for `ignored` entries. Reviewed function names
must be unique across the selected profiles.

An observed caller-owned structure is described below its function:

```toml
[[functions.contexts]]
argument = 0
status = "reviewed"
name = "state"
type-name = "VendorPhyState"

[[functions.contexts.fields]]
offset = 4
width = 32
status = "reviewed"
name = "pending_events"
display-type = "u32"
description = "Observed event word read and updated by this function."
```

The stable field identity is `(argument, signed byte offset, width)`. It must
match generated evidence exactly. Names and `display-type` improve the report;
they do not define a Rust layout, alignment, ownership, aliasing, initialization
state, or synchronization rule. The optional description is one line.

The same physical structure can appear through several functions or through a
relocated data symbol. Pack schema 3 can explicitly unify those observations
as one reviewed logical type:

```toml
[[types]]
id = "vendor-phy-state"
name = "VendorPhyState"
description = "Project-owned interpretation of the observed PHY state object."

[[types.bindings]]
profile = "rom-phy"
source = "rom"
name = "enable-state"
kind = "argument"
function = "rom::phy_enable"
argument = 0

[[types.bindings]]
profile = "archive-phy"
source = "libphy"
name = "static-state-reference"
kind = "global"
member = "state.o"
symbol = "phy_state"

[[types.fields]]
offset = 4
width = 32
status = "reviewed"
name = "pending_events"
display-type = "u32"
description = "Observed event word shared by the bound projections."
```

An argument binding identifies one exact generated function and ABI argument.
A `global` binding identifies completed relocation evidence by its
source/member/symbol tuple. Here `member` is the archive member containing the
relocation, not a claim that this is the symbol's linker-selected definition;
for a linked image it is absent. Multiple bindings are the reviewer's explicit
claim that the observations belong to one logical type. Matching offsets alone
never create that claim.

Pointer-bearing RAM cells are modeled explicitly instead of being flattened
into a global-only special case. For example, a structure reached by loading
the pointer stored in `g_state` is bound as:

```toml
[[types.bindings]]
profile = "archive-phy"
source = "libphy"
name = "runtime-state-pointee"
kind = "dereferenced"
pointer-kind = "global"
pointer-member = "state.o"
pointer-symbol = "g_state"
pointer-offset = 0
```

`pointer-kind` may be `argument`, `global`, or `absolute`; the corresponding
keys are `pointer-function` plus `pointer-argument`, `pointer-member` plus
`pointer-symbol`, or `pointer-address-space` plus `pointer-address`.
`pointer-offset` identifies the pointer cell relative to that root. The
observed field offset remains relative to the loaded pointee. Dynamic pointer
arithmetic is retained as incomplete memory provenance and cannot be promoted
to a reviewed fixed field.

Validation requires every binding to match generated evidence and rejects
binding one object to several logical types. Several observed widths may share
an offset: for example, a byte field can overlap a word access made while
copying the containing structure. Each exact `(offset, width)` remains a
separate evidence and review item. Omitted observed entries are counted as
unreviewed. Logical names and display
types remain presentation claims: they do not prove a C or Rust layout,
alignment, ownership, aliasing, initialization, synchronization, or linker
identity.

## Review states

Every entry present in the sparse overlay has an explicit state:

| State | Meaning |
| --- | --- |
| `reviewed` | attach the required human claims and include them in the report |
| `ignored` | record an intentional decision not to model this observation; names are forbidden |

Generated observations absent from the overlay are implicitly unreviewed.

Ignoring a function also covers its observed contexts and fields. Ignoring a
context covers all observed fields for that argument. A field may be ignored
individually. This makes `--deny-unreviewed` usable without forcing meaningless
names onto scratch or irrelevant state.

## Incomplete evidence

Function review distinguishes three closure conditions:

- the selected function's direct analysis completed;
- its reachable call graph closed;
- affine projection of relevant pointer accesses back to root arguments
  completed.

A function with any incomplete condition cannot become `reviewed` by accident.
After reading its blockers, the reviewer may add:

```toml
accept-incomplete = true
```

This records acceptance of the limitation; it does not make the IR complete.
The generated report keeps the blockers and counts accepted incomplete
functions. Verification and reference generation retain their own stricter,
fail-closed eligibility rules.

## Relationship to interfaces and registers

A function report may show `rtos.queue.send-from-isr`, an observed trampoline
call, and a context write at `arg0 + 0x4`. Those are independent facts:

1. a validated interface call site came from generic pointer provenance and
   matches an exact reviewed anchor/slot plus a caller inside the recovered
   reachable set;
2. linked-IR semantic operations, call sites, and paths remain generated IR
   evidence and are reported separately;
3. the context field name came from this pack.

The join reports instruction address, call kind, and each currently
recoverable register argument expression. If linked IR contains exactly one
call record for the same caller and instruction address, the report also shows
its target, IR argument expressions, and factorized CFG guard alternatives.
Zero or multiple matches stay visibly absent or ambiguous; semantic names are
never used as a fallback join key. When the exact linked-IR call and reviewed
interface slot both carry semantic operation IDs, disagreement is a validation
error rather than two competing labels in the report. Guards constrain a
static path but do not
prove that it executes. The join deliberately does not claim runtime call
order, branch feasibility, missing/unknown argument values, return values,
callee side effects, or scheduler/storage behavior. Turning these static sites
into ordered typed IR actions still requires explicit effect contracts and a
flow-aware ordering representation.

The function pack must not repeat the callback-table offset or prototype. It
also must not name an MMIO address or bit field. Register review links the same
generated functions to the register model, while the function report gives a
source-like reading order. Both views point at shared generated evidence but
neither imports the other's reviewed claims.

## Current limits

The initial workspace template lists only symbol-prefix root functions so a
new pack stays tractable, and root functions remain the strict coverage gate.
The generated report also renders every reachable internal function included
by the selected IR profiles. A reviewer may add an exact internal identity to
the pack to name that function and its observed contexts without requiring a
whole-library coverage claim. Logical types explicitly unify reviewed
memory-object projections, but the tool does not infer those bindings, prove
native layout/aliasing properties, rewrite pseudo-code with reviewed
identifiers, or generate compilable Rust from the report.

Those are deliberate next layers. First the project records stable names and
which incomplete observations were consciously accepted; only then can a
higher-level structured IR safely reuse that vocabulary.
