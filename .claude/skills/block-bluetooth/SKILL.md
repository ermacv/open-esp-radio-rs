## Port

`LeRadioPort` (`crates/protocols/bluetooth/le/radio/src/port.rs`) has no extension traits: optional roles, PHYs, link acknowledgement, receive-wait limits, the horizon and the timing are `LeRadioCapabilities` behind the port's capabilities marker `type Caps: LeCapabilities` (`const CAPS`, known when the image is built; the S31 marker is `BluetoothCapabilities<C, pools…>`, built from the radio config `C` with the radio's own `capabilities`/`radio_timing`). Every request carries `Supported<K, _>` values: the core builds them through `K` (timed ones `Supported::placed` at its `now`, with the one reservation function `RadioTiming::reservation` the backend also uses), so a backend refuses nothing they exclude and an overlap is a backend `debug_assert`; a Host request `K` excludes is an HCI status when the command is taken, and `serves_the_core` (LE 1M at 0 dBm, the DLE maximum with its MIC) is a `const` check where the core is created. Refusals left are the world's (`Late`, `ClockUnavailable`, `EpochExhausted`) and those of the role, event and accept-list state (`Unknown`, `AlreadyConfigured`, `NoInstance`, `Busy`, `ListFull`, `NotListed`); an S31 structure that disagrees is a `RadioFault`, not a refusal. The S31 long recurring receive wait counts two-microsecond units, so the radio rounds an odd wait up (`recurring_wait`). `now`, `submit`, `cancel`, `lifecycle` and `next_event` are async (a fresh controller-time latch per request; the trait's documentation), `clock_info`, `view` and `activity` synchronous. The S31 backend is `BluetoothRuntime` (`runtime.rs`): its `install` returns the port `BluetoothPort` and the composition's `BluetoothControl` (`crates/runtime/esp32s31/bluetooth/src/port.rs`), whose `uninstall` (consuming both) is the backend's own operation; shared-PHY maintenance never pauses the port (it runs under the arbiter lease with the vendor grant-protect brackets, and an event that loses RF ends as an ordinary outcome); no call is refused as not installed. The composition's `start` returns the port with the `BluetoothSystem`, `BluetoothHciService::run` borrows it and `BluetoothSystem::stop` takes it back. `NoRadio` is the host stub. `oer_bluetooth_runtime::serve` is the port's one outcome consumer.

## Traps

- The LE radio clock is the controller clock extended from its 32-bit latch, with no relation to the monotonic clock (`BluetoothRuntime::clock_info` publishes `monotonic: None`): never convert an `LeInstant` through monotonic time. The runtime samples it at least every `TIME_REFRESH` (60 s) to keep the extension; the modem LP timer is an alarm of its own domain, armed through a port operation, never an `oer_time::Timer`.
- Controller time has two raw ticks per microsecond; fractional ticks round down, and scheduler positions wrap only inside the driver (`driver/bluetooth/README.md`, "Controller time"). A raw captured anchor is not a packet-start timestamp (catalog section `bluetooth-peripheral-timing-limits`). The S31 radio epoch starts 2^32 µs above zero and ends 2^32 µs below `u64::MAX` (`radio.rs`, `EPOCH_MARGIN`), so every capture and its packet-start correction are representable by construction; a sample past the end reports the epoch exhausted (`ClockError::EpochExhausted`) instead of advancing.
- Events never overlap: the Controller core resolves role conflicts through one arbiter and places every window with the reservation function the backend shares (`RadioTiming::reservation`), so the S31 radio meets no overlapping window (a `debug_assert`, not a refusal) and never moves one. The radio role holds no register; the caller serializes every entry (`BluetoothRadio`).
- `serve` goes on after `EventsLost` (only advertising and scan reports can be lost; ends and connection data hold reserved slots). Radio epoch exhaustion has one exit, `ServeExit::EpochExhausted`, from the clock (`ClockError`/`RequestError::EpochExhausted`) or from planning (`oer_bluetooth_controller::EpochExhausted`, the planner's only error); every other planning failure is unrepresentable by type.
- `serve` owns the port session: it ends every exit but `Poisoned` with the managed stop (`Disable`, then every outcome into the core until `Disabled`) and returns `Served`. Never cancel it mid-run: the core would be left mid-request and the port enabled, and the S31 `uninstall` refuses a port that is not disabled (`BluetoothUninstallError::NotDisabled`). The S31 `Disable` stops the scheduler first, so a listed event ends with its recorded completion, `NotExecuted` when its start lay ahead of the stop, or `EventResult::Aborted` when it started without a status; admitted events and the reports nothing acknowledges always leave one queue slot for a lifecycle terminal, and a closing command holds its own reservation, so a `Disable` finds room unless the consumer left earlier terminals unread.
- Controller memory is initialized internal SRAM (`.dma.data.open_radio_bluetooth_*`, the `controller_memory!` sections), not a zeroed `.bss` region, and is claimed once per boot (`BluetoothMemoryError::AlreadyClaimed`): host bonds and connections do not survive a restart (source fact `bluetooth-same-storage-powered-restart`).
- Lifecycle: power and clock failures roll back to the parked client; any failure after the first Controller write keeps its owners fail-stop until reset. RF closes only when the last PHY client leaves the shared radio. Initialization and scheduler `RUN` are not RF evidence.
- PHY order: `esp_phy_enable(PHY_MODEM_BT)` and BTBB after the controller HAL init; unlike IEEE 802.15.4, Bluetooth keeps the transmit-on delay the first BTBB initialization writes (`bluetooth_client.rs`). The vendor's modem ETM channel zero belongs to IEEE 802.15.4 here, so production routes channel two (`verification/esp32s31/README.md`, BLE PHY register initialization).
- Three interrupt sources (124, 127, 133) go to one dispatcher; both HAL owners are installed before any CPU route is enabled (`bluetooth_interrupt.rs`).
- Interrupt model ([ownership and refusals](../../../docs/architecture.md#ownership-and-refusals), #643): the hardware scheduler keeps the air timing, so the primary interrupt only services the Controller's status through its interrupt owner and signals the worker (`on_scheduler_wake`); every decision is the worker's. The async mutex left between the worker and the port calls goes when the runner joins the port's body (#581); never move scheduling logic into the interrupt.
- Narrow on purpose: LE 1M only for connections, no peripheral latency, one peripheral connection in the product (the Controller core holds `CONNECTIONS` of them, set by the composition; #376 raises it), 0 dBm for every role, LE 2M and Coded only in DTM, always awake on the main-XTAL profile (no modem or LP sleep). Feature bits stay clear until a production path is complete; a recovered register, SRAM layout, parser or DTM-only PHY never grants advertisement (catalog section `bluetooth-capability-advertisement`).
- Coexistence: each epoch enables Bluetooth coexistence at start and disables it at stop after withdrawing every status bit (composition `coex.rs`). Alone on the antenna every event requests it at the highest priority (role `coexistence.rs`); PHY tracking belongs to `RadioSystem::run_tracking` and does not wait for a gap between Bluetooth events.
- Secure GATT accepts only LE Secure Connections Numeric Comparison; Just Works, passkey, OOB and legacy pairing are not fallbacks (`adapters/trouble/bluetooth/gatt/README.md`).
- The controller archives' symbols are obfuscated and change between releases: a vendor leaf names the symbol of the pinned release; source names come from `verification/esp32s31/facts/names/` (grep only).
