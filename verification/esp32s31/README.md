# ESP32-S31 vendor references

## Pinned vendor artifacts

[`artifacts.toml`](artifacts.toml) is the single pin of every ESP32-S31
vendor archive, the ROM ELF, the ESP-IDF files and the vendor firmware
outputs production follows: upstream repository, revision, path and SHA-256
of each fetched artifact, and for the firmware outputs the catalog image
whose tracked recipe builds them, with no digest. Fetch the pinned artifacts
into `target/vendor/<source>/<revision>/` with

```console
cargo xtask vendor fetch esp32s31
```

which verifies every file; `--artifact rom` fetches only the ROM ELF the
image pipeline's interrupt stack check reads. The firmware outputs (`sdk`,
`phy-sdk` and the ESP-IDF component archives `libesp-hw-support` and
`libhal`) are the bootloader, image and archives of the
[`phy-tracking-reference`](hil-vendor/README.md) catalog project, built with

```console
cargo hil firmware build phy-tracking-reference
```

The `esp-idf` files are the IEEE 802.15.4 driver sources the
[MAC engine](../../crates/hardware/espressif/ieee802154/engine/README.md) is
ported from and the headers they include; `esp-idf-phy` is ESP-IDF's
`esp_phy` component at the same revision, read for the vendor PHY path
(enable, tracking and modem retention). Changing a pin means changing the
manifest; production follows the pinned behaviour. Hashes in reviewed
register evidence and reference notes record the artifact a fact was
observed in; they are not pins.

## Contents

| Path | Contents |
| --- | --- |
| `artifacts.toml` | Pins of every vendor archive, ROM ELF, ESP-IDF file and firmware output |
| `facts/provenance.toml` | Reviewed code fingerprints of the vendor functions production `SOURCE:` blocks cite |
| [`facts/names/`](facts/names/README.md) | Source names for generated function names of the pinned Controller archive, regenerated by [`oer-symbol-lineage`](../../tools/symbol-lineage/README.md) |
| [`hil-vendor/`](hil-vendor/README.md) | Vendor firmware the HIL stand runs: the calibration, BLE scan and IEEE 802.15.4 references, and the `phy-tracking-reference` link environment |

Private vendor artifacts never enter the repository. Necessary recovered
hardware tables belong in production source with provenance, as defined by
the [source policy](../../docs/source-policy.md). The
[technical references](../../docs/vendor/esp32s31/README.md) describe the
Bluetooth Controller, DTM, advertising, scanning, connection and IEEE
802.15.4 boundaries of the pinned code.

## Register publication

Register review and publication belong to the independent
[register tool](../../tools/registers/README.md):

```console
cargo registers generate --manifest registers/esp32s31/publication/registers.toml --check
```
